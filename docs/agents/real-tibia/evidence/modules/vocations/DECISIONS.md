# Vocations evidence decisions

| Decision | Selected evidence and constraint | Rejected alternative |
|---|---|---|
| Use one shared `vocations` dossier | The canonical registry treats all vocation variants as entries in one XML-backed lifecycle. | Separate Knight/Paladin/Sorcerer/Druid/Monk dossiers would create duplicate module identities. |
| Compare only public HP/mana/cap gains and promotion titles | The current official manual publishes this exact table, and Canary XML exposes directly comparable definitions. | Comparing hidden formulas or broad combat balance from public prose would overclaim authority. |
| Classify correspondence as static conformance | Official guide plus exact Canary XML/source support a bounded cross-source comparison. | Calling it gameplay or runtime parity is rejected because no controlled execution was selected. |
| Preserve runtime application as `UNKNOWN` | TSD-003 explicitly leaves runtime validation unassessed, and source presence is insufficient. | Inferring successful level-up/promotion behavior from loader code is rejected. |
| Create one feature-owner request | A controlled runtime result belongs to the feature owner and is reusable as retained evidence. | Adding Collector tests, execution infrastructure or runtime code is prohibited. |
| Keep combat, spells, weapons and Wheel outside scope | They are descriptive interactions and separately owned modules. | Absorbing them would destroy the low-coupling pilot boundary. |
| Use exact date/release/commit axes | Monk announcement, release and current Canary commit are independently source-pinned. | A generic `version` field is forbidden. |
